# SPEC: Permissions P2b — The Context-less Write Guard

## Summary

This feature makes a database write with no action context a bug that fails loudly in dev and test (design §5, "A write without a context"):
- **The guard.** `KodaPrismaClient` is the API's Prisma client: the generated `PrismaClient` with a query extension that checks every guarded write for a current `ActionContext`. With no context, a guarded write throws `ContextlessWriteError` in dev and test. In production (`ENV_NAME` or `NODE_ENV` is `production`) it logs an error and runs as `SYSTEM/unknown`, so an audit gap never becomes an outage. `AppModule` passes `KodaPrismaClient` to `PrismaModule`, so the guard covers every model write and raw execute through `PrismaService`, including interactive transactions. Raw `$queryRaw` statements are not guarded (see the designer's calls).
- **The outbox relay.** The relay's own bookkeeping writes (`markPublished`, `markRetry`, `markDead`, and `recordLastError` after a failed fan-out) run outside any request, so they run as `SYSTEM/outbox`.
- **Strict tests.** New test helpers (`withTestActor`, `asTestActor`, `fixtureDb`, `expectGuardActive`) let the DB-backed suite keep writing under the guard. Every integration and e2e spec that writes through the booted `AppModule` outside an HTTP request is converted: fixture writes go through `fixtureDb(app)` (as `SYSTEM/seed`), and direct service calls that write run with an explicit test actor.

This is the second of seven features implementing phase P2 of `docs/superpowers/specs/2026-10-18-permission-approval-redesign-design.md`. The order (ruled 2026-10-24): context, **context-guard**, audit-entry, audit-core, audit-fleet, audit-integrations, web.

## Motivation

`permissions-p2-context` (PR #325) made every request, tool call, system writer and outbox handler set an `ActionContext`. Nothing yet enforces it, so a new entry point that forgets the context writes rows with no recorded actor, and the audit features after this one would record nothing for them. Design principle 5 states the rule: "A write without one is a bug: dev and test throw; production records `system:unknown` and logs an error."

Today:
- `AppModule` passes the generated `PrismaClient` to `PrismaModule.forRootAsync` (`src/app.module.ts:90`), so no write is checked.
- The outbox relay of `@nathapp/nestjs-outbox` runs on its own interval. Its bookkeeping writes in `PrismaOutboxStore` and `PrismaOutboxRepository.recordLastError` run with no context; p2-context left them to this feature.
- 194 integration and e2e specs boot `AppModule` and write through it outside any request: through the fixture client they take from `app.get(PrismaService).client`, or by calling a writing service or repository directly. Under the guard every one of those writes would throw.

**Rulings that bind this feature** (user, 2026-10-24):
- **Keep the design approach.** The rule is enforced at the Prisma client, strict in tests. `@nathapp/nestjs-audit`'s `AuditInterceptor` is not used.
- **Strict in tests.** The integration suite is converted, not exempted: a `withTestActor()` helper, and every direct service call wrapped.
- **The guard is wired first** (US-002), before the conversions. Each conversion story then sees real `ContextlessWriteError` failures in its scoped integration run, which gives it a failing test to start from. The branch's integration suite stays red until US-010, and only the PR's CI sees that; the unit gate stays green throughout.
- **Fixture writes run as `SYSTEM/seed`** through `fixtureDb(app)`. No new production system id is added.

## Design

### Designer's calls (not ruled by the user; change them in review if wrong)

- **Which operations are guarded.** Model writes (`create`, `createMany`, `createManyAndReturn`, `update`, `updateMany`, `updateManyAndReturn`, `upsert`, `delete`, `deleteMany`) and raw executes (`$executeRaw`, `$executeRawUnsafe`). Reads are not guarded, and neither are `$queryRaw` and `$queryRawUnsafe`: SQL cannot be classified without parsing it. Eight `$queryRaw` statements write, and they pass the guard unchecked:
  - `PrismaOutboxStore.claimBatch` (`src/outbox/prisma-outbox.store.ts`): `UPDATE "OutboxEvent"`.
  - The `ChatThread.nextSeq` bump in `src/fleet/threads/domain/chat-thread.domain.ts`.
  - `src/fleet/schedules/prisma-schedule.repository.ts`: `UPDATE "FleetJob"`, the coalesce count.
  - `src/fleet/ingest/prisma-bundle-ingest.repository.ts`: the ingest row claim.
  - `src/fleet/budgets/prisma-budget.repository.ts`: `INSERT INTO "BudgetIncident"`.
  - `src/fleet/jobs/prisma-fleet-job.repository.ts`: the job's `ASSIGNED` transition.
  - `src/notifications/fleet/fleet-health-alerts.repository.ts`: `INSERT INTO "FleetHealthAlert"`.
  - `src/email/schedule/email-schedule.repository.ts`: `claimDue`.

  Each except `claimBatch` sits in a flow that p2-context already runs inside a context: a request or a wrapped system writer. `claimBatch` runs on the relay's own interval with no context (see the next call).
- **Mode by `ENV_NAME` or `NODE_ENV`, no config flag.** The mode is `record` when either is `production` (the shipped API image sets only `ENV_NAME=production`, `apps/api/Dockerfile:99`; `src/config/rag.config.ts` checks both the same way), and `throw` otherwise. The mode is read once, when `KodaPrismaClient` is constructed. A switch to turn the guard off would undo the rule.
- **The guard's logic lives in `src/action-context/contextless-write.ts`**, next to the context it checks, and imports nothing from the generated Prisma client. The Prisma extension that installs it, and `KodaPrismaClient`, live in `src/prisma/koda-prisma-client.ts`, next to `createPgAdapter` (`.nax/rules/api-data.md` confines Prisma value imports).
- **`claimBatch` is not wrapped.** It is a `$queryRaw` and so not guarded. Giving it an actor is left to the audit features.
- **`PrismaOutboxStore` declares `@SystemWriter('system.outbox.dispatch')`**, the key its sibling `FanOutPublisher` already declares: the relay's bookkeeping is part of the same dispatch (`.nax/rules/api-core.md`: every class that writes as the system declares its key). Its wraps use `runAsSystemWriter(this, …)`.
- **`expectGuardActive` probes with `$executeRaw\`SELECT 1\``.** That is a guarded operation that changes no data, so the sentinel test needs no fixture row.

### Prisma promises are lazy

A Prisma call returns a `PrismaPromise`, which runs its query when it is awaited, not when it is created, and runs it in the async context of the awaiter. So `runAsSystem('outbox', () => client.x.updateMany(…))` returns the lazy promise out of the context, and the query then runs with no context. **Every `runAs*` or `withTestActor` callback in this feature awaits its Prisma call inside: `runAsSystem('outbox', async () => { await client.x.updateMany(…); })`.** The same applies to the guard's record mode (`runAsSystem('unknown', async () => await query(args))`) and to the test helpers. ACs pin this with a lazy thenable double: an object whose `then` records `currentContext()` only when it is awaited.

### The guard core (US-001)

`src/action-context/contextless-write.ts`:

```typescript
import { Logger } from '@nestjs/common';
import { currentContext, runAsSystem } from './action-context';

export type WriteGuardMode = 'throw' | 'record';

export const GUARDED_OPERATIONS: ReadonlySet<string>;   // the eleven operations listed above

export class ContextlessWriteError extends Error {
  readonly name = 'ContextlessWriteError';
  constructor(readonly operation: string, readonly model?: string);
  // message: `write outside an action context: <model>.<operation>`, or `…: <operation>` when model is undefined
}

/** `record` when `env.ENV_NAME` or `env.NODE_ENV` is `'production'`, else `throw`. */
export function resolveWriteGuardMode(env: { ENV_NAME?: string; NODE_ENV?: string }): WriteGuardMode;

export interface GuardedOperationParams {
  model?: string;
  operation: string;
  args: unknown;
  query: (args: unknown) => PromiseLike<unknown>;
}

/** The `$allOperations` hook: passes reads and in-context writes to `query`, applies `mode` to the rest. */
export function contextlessWriteHandler(mode: WriteGuardMode): (params: GuardedOperationParams) => Promise<unknown>;
```

The handler, for an operation in `GUARDED_OPERATIONS` with `currentContext()` undefined:
- `throw`: rejects with `ContextlessWriteError(operation, model)` without calling `query`.
- `record`: logs `write outside an action context: <model>.<operation>` at error level through a `Logger` from `@nestjs/common`, then returns `runAsSystem('unknown', async () => await query(args))`.

Every other call returns `await query(args)`, and a rejection from `query` propagates unchanged. The top-level `$allOperations` hook (not `$allModels`) is used because it also receives the raw operations, with `model` undefined.

### The client and its wiring (US-002)

`src/prisma/koda-prisma-client.ts`:

```typescript
import { PrismaClient, Prisma } from '../generated/prisma/client';
import { contextlessWriteHandler, resolveWriteGuardMode, WriteGuardMode } from '../action-context/contextless-write';

/** The top-level `$allOperations` hook also receives raw operations, with `model` undefined. */
export function contextlessWriteExtension(mode: WriteGuardMode) {
  return Prisma.defineExtension({ name: 'contextless-write-guard', query: { $allOperations: contextlessWriteHandler(mode) } });
}

/** The API's Prisma client: the generated client with the context-less write guard (design §5). */
export class KodaPrismaClient extends PrismaClient {
  constructor(options: Prisma.PrismaClientOptions) {
    super(options);
    // PrismaService does `new options.client(options.clientOptions)`, so the extended client returned here is the
    // one every repository, the transaction manager and every interactive transaction use. The returned object is
    // not `instanceof KodaPrismaClient`; nothing in the API checks `instanceof PrismaClient`.
    return this.$extends(
      contextlessWriteExtension(resolveWriteGuardMode({ ENV_NAME: process.env['ENV_NAME'], NODE_ENV: process.env['NODE_ENV'] })),
    ) as unknown as KodaPrismaClient;
  }
}
```

`AppModule`'s `PrismaModule.forRootAsync` factory passes `client: KodaPrismaClient`; `clientOptions` and `transaction: true` are unchanged. The extended client sets `$on` to undefined, which `PrismaService` uses only when `logging` is set, and koda never sets it.

### The outbox relay (US-003)

- `PrismaOutboxStore` (`src/outbox/prisma-outbox.store.ts`) gains `@SystemWriter('system.outbox.dispatch')`. `markPublished`, `markRetry` and `markDead` await their `updateMany` inside `runAsSystemWriter(this, async () => { … })`.
- `FanOutPublisher.publish` (`src/outbox/fan-out-publisher.ts`) awaits its `recordLastError` call inside `runAsSystem('outbox', async () => { … })`. The `warn` when recording fails and the thrown `OutboxFanOutError` are unchanged.
- `PrismaOutboxStore.save` is unchanged: it writes in the producer's transaction, so in the producer's context.

### Test helpers (US-004)

`apps/api/test/helpers/action-context.ts`:

```typescript
import type { INestApplicationContext } from '@nestjs/common';
import type { ActionActor } from '../../src/action-context/action-context';
import type { PrismaClient } from '../../src/generated/prisma/client';

/** Runs `fn` inside a context with `actor` and awaits it there (Prisma promises are lazy). */
export function withTestActor<T>(actor: ActionActor, fn: () => T | PromiseLike<T>): Promise<T>;
/** A view of `target` whose function properties run through `withTestActor(actor, …)`. */
export function asTestActor<T extends object>(target: T, actor: ActionActor): T;
/** The app's Prisma client; every model and raw call is awaited inside `runAsSystem('seed', …)`. */
export function fixtureDb(app: INestApplicationContext): PrismaClient;
/** Resolves when the app's Prisma client refuses a context-less write; rejects otherwise. */
export function expectGuardActive(app: INestApplicationContext): Promise<void>;
```

- `withTestActor` maps the actor type to an origin: `USER` and `AGENT` → `rest`, `RUNNER` → `runner`. A `SYSTEM` actor runs through `runAsSystem(actor.id, …)`, so an id outside `SYSTEM_ACTOR_IDS` throws `unknown system actor id: <id>`. `fn`'s result is awaited inside the context.
- `asTestActor` returns a `Proxy`. Reading a function property gives a function that calls the original with the target as `this` inside `withTestActor`, so it returns a promise; use it for services whose writing methods are async. Other properties pass through unchanged.
- `fixtureDb` reads `app.get(PrismaService, { strict: false }).client` and returns a proxy over it. Each call to a model delegate method, `$transaction`, `$executeRaw`, `$executeRawUnsafe`, `$queryRaw` or `$queryRawUnsafe` is awaited inside `runAsSystem('seed', …)`. Other properties pass through. The array form `$transaction([…])` is not supported, because the proxied calls return started promises rather than Prisma promises. The interactive form works, and its callback runs inside the `seed` context.
- `expectGuardActive` runs `` client.$executeRaw`SELECT 1` `` on the app's raw client (`app.get(PrismaService, { strict: false }).client`) outside any context. It resolves when that rejects with `ContextlessWriteError`. Otherwise it rejects with `Error('the application Prisma client does not refuse context-less writes')`.

### Converting a spec (US-005 to US-010)

**Which specs.** A spec is converted when it boots `AppModule` and writes outside an HTTP request: through the client from `app.get(PrismaService).client`, or by calling a writing service, repository, ingestor, processor or transaction manager directly. The converted specs are the ones listed under each story in `### Modifies`. A spec that boots `AppModule` but writes only through HTTP or through `createTestPrismaClient()` is not converted.

In each converted spec:
1. **Fixtures.** The client the spec takes from `app.get<PrismaService<PrismaClient>>(PrismaService).client` (or `app.get(PrismaService).client`, `moduleRef.get(PrismaService, { strict: false }).client`, or `.client` of a kept `PrismaService`) for fixture writes and assertion reads becomes `fixtureDb(app)`. Shared helpers that take a client parameter (`seedFleetHttpWorld`, `seedFleetBase`, `insertRunner`, `grantRole`, `grantBaseline` and the rest) are passed `fixtureDb(app)`; the helpers do not change. A fixture client from `createTestPrismaClient()` stays as it is: it is not guarded.
2. **Direct calls.** A direct call that writes, made outside an HTTP request, runs inside `withTestActor(actor, () => …)`, or through `asTestActor(service, actor)` when the spec calls the same service several times. The actor is the one production carries for that call:
   - the request principal for a method a route reaches (the user or agent the test acts as);
   - the job's runner (`{ type: 'RUNNER', id }`) for a job-transition effect such as `ThreadJobEffects.onJobEnded`;
   - `{ type: 'SYSTEM', id: <component> }` for a background entry the test calls below its wrapped entry:

     | Direct call | Wrapped entry in production | Actor |
     |:--|:--|:--|
     | `ThreadIngestor.catchUp`, `PrismaThreadIngestRepository.fold` | `ThreadIngestBootstrap` | `thread` |
     | `ScheduleTicker.tick` | `runOnce` | `schedule` |
     | `FleetLogRetentionProcessor.purge` | `scheduledPurge` | `log` |
     | `BundleIngestService.drain` | the drain `kick` chains | `ingest` |
     | `EmailDispatcher.tick`, `EmailDispatcher.sendOne` | `runScheduledTick` | `email` |
     | an outbox subscriber's `handle` | `FanOutPublisher.publish` | `outbox` |
     | `VcsPrSyncService.applyMergedPr` | the VCS webhook and poll | `vcs` |

   - `NotificationWriter.deliver` takes the actor of the flow the test stands in for: the request principal when the test plays a route, `outbox` when it plays a subscriber.
3. **No wrapper needed** for entries p2-context already wraps (`ScheduleTicker.runOnce`, `FleetSweeper.sweep`, `PendingActionExpirySweeper.tick`, `ApprovalExpirySweeper.tick`, `BudgetSweeper.tick`, `FleetPrStateRefresher.refresh`, the retention processors' `scheduledPurge`), for `OutboxRelay.dispatchPendingBatch` (US-003), or for calls made through HTTP (`supertest`).
4. **Narrowest scope.** Wrap the call, never a whole `it` body or hook. A wide wrapper would hide a production path that writes without a context, which is the bug the guard exists to catch.
5. **Sentinel.** Add a test named `writes need an action context` that awaits `expectGuardActive(app)` against the application the spec boots.
6. **A production gap is fixed in production, not wrapped away in the test.** When a spec fails because a production path reached through HTTP or a wrapped entry writes without a context, the story gives that production entry its context (`runAsSystemWriter` or `runAsSystem` with the component of the p2-context system-writer table, awaiting inside) and names the entry in its commit message.

### Failure Handling

| Situation | Behaviour | Story |
|:--|:--|:--|
| a guarded operation with no context, mode `throw` | rejects with `ContextlessWriteError`; `query` is not called, so nothing is written | US-001 |
| a guarded raw operation (`$executeRaw`) with no context, mode `throw` | rejects with `ContextlessWriteError` whose message names the operation alone | US-001 |
| a guarded operation with no context, mode `record` | logs an error, runs the query as `SYSTEM/unknown` and returns its result | US-001 |
| `query` rejects inside the handler | the rejection propagates unchanged | US-001 |
| a guarded write inside an interactive transaction with no context | the write rejects, so the transaction rolls back | US-002 |
| `KodaPrismaClient` constructed with `ENV_NAME=production` | the guard records instead of throwing | US-002 |
| an outbox handler throws during relay dispatch | `recordLastError` writes as `SYSTEM/outbox`; the record is retried as today | US-003 |
| `withTestActor` given a `SYSTEM` actor id outside `SYSTEM_ACTOR_IDS` | rejects with `unknown system actor id: <id>` before running `fn` | US-004 |
| `expectGuardActive` against an app whose client accepts the probe | rejects with `the application Prisma client does not refuse context-less writes` | US-004 |

## Out of Scope

- Guarding `$queryRaw` and `$queryRawUnsafe` is out of scope (designer's call: SQL is not classified). The eight writing `$queryRaw` statements listed in the designer's calls pass the guard unchecked; feature `permissions-p2-audit-integrations` must cover them in its coverage walk.
- Wrapping `PrismaOutboxStore.claimBatch` in a context is out of scope (it is a `$queryRaw`; the audit features decide its actor).
- `BudgetEvaluator.signal`'s deferred evaluation inheriting the first signaller's context is out of scope (feature `permissions-p2-audit-core` decides its actor).
- The `AuditEntry` table, its storage and `GET /audit` are out of scope (feature `permissions-p2-audit-entry`).
- The coverage test that walks every write surface is out of scope (feature `permissions-p2-audit-integrations`).
- A config flag or environment variable that turns the guard off is out of scope (designer's call: the mode follows `ENV_NAME` and `NODE_ENV` only).
- Fixture clients from `createTestPrismaClient()`, and specs that build their own `PrismaModule.forRoot({ client: PrismaClient })`, stay unguarded and are not converted.
- Specs that boot `AppModule` but write only through HTTP or `createTestPrismaClient()` are not converted: `test/e2e/tickets.e2e.spec.ts`, `test/e2e/transaction-manager-wiring.e2e.spec.ts`, `test/e2e/empty-description.spec.ts`, `test/integration/fleet/runner-admin.integration.spec.ts`, `test/integration/permissions/permission-contract.integration.spec.ts`, `test/integration/permissions/system-roles.integration.spec.ts`, `test/integration/permissions/remaining-route-permissions.integration.spec.ts`, `test/integration/permissions/runner-route-permissions.integration.spec.ts`, `test/integration/projects/project-role-permissions.integration.spec.ts`, `test/integration/seed/seed-e2e.integration.spec.ts`, `test/integration/vcs/vcs-permissions.integration.spec.ts`, `test/integration/vcs/vcs-webhook-secret.integration.spec.ts`.
- Unit specs that mock `PrismaService` (module and DI specs, `src/**/*.spec.ts`) are not converted; they never construct `KodaPrismaClient`.
- The Prisma seed scripts under `apps/api/prisma/` keep the plain `PrismaClient` and are not guarded.
- Changing the shared fixture helpers in `test/helpers/` and `src/permissions/test-helpers/` is out of scope; callers pass them `fixtureDb(app)`.
- Adding the `fixtureDb` / `withTestActor` convention to `.nax/rules/api-testing.md` is a manual step after this feature merges, not story work (`.nax/` is read-only to the run).
- Setting the authenticated user as the actor of the public auth and invite routes is out of scope (feature `permissions-p2-audit-core`).
- Regenerating `openapi.json` and `apps/cli/src/generated/` is out of scope; no contract changes.

## Acceptance Criteria

Wording:
- "No context" means `currentContext()` is undefined at the call.
- "A booted application" is `AppFactory.create(AppModule)` initialised as `test/helpers/http-app.ts` does, with `KODA_DB_TESTS=1`.
- "A lazy thenable" is an object whose `then` method records `currentContext()` at the moment it is called (when the object is awaited) and then resolves.

1. [unit] `resolveWriteGuardMode({ NODE_ENV: 'production' })` returns `'record'`.
