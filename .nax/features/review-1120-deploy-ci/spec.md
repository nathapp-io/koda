# SPEC: Review 1120 deploy, CI and release fixes

## Summary

This feature fixes the deployment, CI and release findings of the 2026-11-20 whole-repo review
(`docs/20261120-review-whole-repo-consolidated.md`): K1, K3, K4, K5, K6, K7, K8, K19 and K20, plus one defect found
while grounding this spec (N1, `rollback.sh` fails on macOS). The API, CLI, web and runner findings are separate
features.

1. **CI change filter (K7, K19).** The `changes` job no longer skips every gated job when a PR changes more paths than
   one pipe buffer holds, and `openapi-ts.config.ts`, `deployments/` and the root `docker-compose.yml` count as code
   paths for both PRs and `main` pushes, so the new deployment-script tests run when only those files change.
2. **Release channels (K8).** A release moves the floating Docker tags (`latest`, `<major>.<minor>`), the npm `latest`
   dist-tag and the GitHub "latest release" flag only when it is the newest stable version for that channel. A
   re-publish of an older tag, or a back-port tag, no longer moves them backwards.
3. **Compose and test inputs (K1).** Both Compose files pass the two webhook signature switches to the API, and the
   `apps/api` test task re-runs when workflow, deployment or script files change.
4. **Backup (K3, K6).** `backup-db.sh` always takes and verifies a Postgres dump (starting the bundled database when it
   is stopped) and archives the data volume through the Compose project instead of a hardcoded volume name.
5. **Rollback preflight (K4).** `rollback.sh` validates the restore archive and pulls the target images before it
   stops anything.
6. **Rollback restore and `.env` (K3, N1).** `rollback.sh` restores through the Compose project and updates `.env`
   without GNU-only `sed -i`.
7. **Deploy (K5, K6).** `deploy.sh` refuses a `DATABASE_URL` override in `.env`, and stops before migrating when the
   pre-deploy backup fails.
8. **Docs and cleanup (K5, K20).** The example deployment documents bundled Postgres only, and the broken
   `scripts/seed.sh` is deleted.

## Motivation

- **K7.** `.github/workflows/ci.yml` (`changes` job, step `filter`) runs
  `printf '%s\n' "$changed" | grep -qE "$CODE_PATHS"` under `set -euo pipefail`. `grep -q` exits at the first match, and
  if `printf` still has output it dies with SIGPIPE (141). The pipeline then counts as false, the step writes
  `code=false`, and quality, test and smoke are skipped, which counts as passing. Reproduced with 5,000 `apps/` paths
  (231 KB): `skip`, `PIPESTATUS` `141 0`.
- **K19.** `openapi-ts.config.ts` drives the generated CLI SDK (`responseStyle`, `throwOnError`) and is regenerated by
  the release job, but it is in neither `on.push.paths` nor `CODE_PATHS`.
- **K8.** `release.yml` step `Compute Docker tags` tags every stable build `:<tag>`, `:<major.minor>` and `:latest`, and
  step `Set release info` publishes every stable CLI with npm dist-tag `latest`. A `workflow_dispatch` re-publish of an
  existing tag (its documented purpose) or a pushed back-port tag (`v0.3.5` after `v0.4.2`) moves all three backwards.
  The GitHub Release step does not set `make_latest`, so GitHub marks the newest-created release as latest.
- **K1.** Both Compose files whitelist API environment variables and omit `CI_WEBHOOK_REQUIRE_V2` and
  `WEBHOOK_SIGNATURE_V1_ENABLED`, so an operator who follows `docs/deployment/webhooks.md` gets the defaults
  (`ciRequireV2: false`, `v1Enabled: true`) regardless of what they set.
- **K3.** `backup-db.sh` archives, and `rollback.sh` clears and restores, the hardcoded volume `koda-local_koda_data`.
  With `COMPOSE_PROJECT_NAME=koda-staging` the API mounts `koda-staging_koda_data`, so backup reads the wrong volume
  and restore overwrites the default deployment's data.
- **K6.** `backup-db.sh` skips the Postgres dump when the `postgres` service is not running and still exits 0. A
  stopped stack keeps its database volume, and `deploy.sh` then runs `prisma migrate deploy` (which starts Postgres
  through `depends_on`) with no dump taken.
- **K4.** `rollback.sh` runs `docker compose stop api web` before it checks that the `--restore-db` file exists, so a
  typo exits 1 with both services stopped.
- **N1.** `rollback.sh` updates `.env` with `sed -i "s/^KODA_VERSION=.*/.../"`. BSD sed on macOS reads the script as a
  backup suffix and fails (`invalid command code`), so under `set -e` the rollback dies after stopping the services and
  restoring the data. Verified on this host's `/usr/bin/sed`.
- **K5.** `deployments/example/README.md` tells operators to set `DATABASE_URL` in `.env` for an external Postgres, but
  the Compose file sets `DATABASE_URL` explicitly from the bundled `postgres` host, so the `.env` value is ignored, and
  migration and backup target the bundled service too. Owner ruling (2026-11-20): the example deployment supports
  bundled Postgres only, and an override is refused.
- **K20.** `scripts/seed.sh` runs `docker exec koda-api ... bun apps/api/prisma/seed.ts`. Compose names the container
  `<project>-api-1`, and the API image copies only `dist`, the schema and migrations, so the seed entry point is absent.
  No document references the script, and the first registered user is the admin (`apps/api/src/config/auth.config.ts`),
  so it has no remaining job. Owner ruling (2026-11-20): delete it.
- **Stale green.** Workflow and script tests live in `apps/api/test/unit/tooling/` (precedent
  `ci-integration-shards.spec.ts`), but turbo hashes only `apps/api` files for `@nathapp/koda-api#test`, so a PR that
  changes only `ci.yml` replays a cached pass in CI. And the `changes` filter has no `deployments/` or
  `docker-compose.yml` entry, so a PR that changes only a deploy script skips the test job altogether.

## Design

### Calls made in this spec

- **Tests live in `apps/api/test/unit/tooling/`** and run under `bun run test` (Vitest globs `test/**/*.spec.ts`), next
  to `ci-integration-shards.spec.ts`. Every story with tests uses `Workdir: apps/api`, and edits repo-root files
  (`.github/`, `deployments/`, `scripts/`, `docker-compose.yml`) listed under `### Modifies`.
- **Workflow steps are tested by running them.** A test extracts the `run: |` body of a named step from the workflow
  text (the step is the YAML list item, starting at its `- ` line and ending at the next sibling `- ` item or a dedent,
  that contains the given `id:` or `name:` line; the body is the indented block after `run: |`), writes it to a
  temp file and runs it, with `GITHUB_OUTPUT` pointing at a temp file and a stub `git` first on `PATH`. The
  assertions read the `key=value` lines written to `GITHUB_OUTPUT`. Expressions `${{ ... }}` never appear inside these
  bodies (review E/SEC-9 already routes inputs through `env:`), so the extracted text runs as is. The extractor removes
  the block's common indentation, and the test runs the body with `/bin/bash -e <file>`, which is how GitHub runs a
  `run:` step with no `shell:` key (`bash -e {0}`), using `/bin/bash` explicitly so a newer bash earlier on `PATH`
  cannot hide a bash 3.2 incompatibility. Structural assertions about the workflow (job outputs, a step's `with:` key)
  slice the workflow text, as `ci-integration-shards.spec.ts` does: no YAML parser is a direct dependency of
  `apps/api`.
- **Release logic stays inline in `release.yml`, not in a script file.** A `workflow_dispatch` re-publish runs the
  workflow from `main` but checks out the old tag's commit, where a new script would not exist. Inline logic always
  runs the current rule.
- **Release channel rule.** A stable tag matches `^v[0-9]+\.[0-9]+\.[0-9]+$`. The remote stable tags come from
  `git ls-remote --tags --refs origin 'v*'` (lines `<sha>\trefs/tags/<tag>`; canary and other non-stable tags are
  ignored). Versions compare numerically per component, so `v0.10.0` is newer than `v0.9.9`. For a stable `TAG`:
  - `latest=true` when `TAG` is equal to or newer than every remote stable tag.
  - the `<major>.<minor>` alias moves when `TAG` is equal to or newer than every remote stable tag with the same major
    and minor.
  - npm dist-tag: `latest` when `latest=true`; else `release-<major>.<minor>` when the `<major>.<minor>` alias moves;
    else `backport-<version>` (for example `backport-0.4.1`), a tag no other version uses. An older version must still
    be published under some dist-tag, npm rejects a dist-tag that parses as a semver range, and a shared tag must never
    move to an older version.
  - Docker tags: always `:<TAG>`, plus `:<major>.<minor>` when the alias moves, plus `:latest` when `latest=true`.
  - A canary tag keeps today's behaviour: Docker `:canary` only, npm `canary`, and `latest=false`.
  - When `git ls-remote` fails, the step fails, so nothing is published under a floating tag on a guess. The step body
    starts with `set -euo pipefail` and captures the listing into a variable (`remote_tags=$(git ls-remote ...)`)
    before parsing it; a process substitution or a pipe into a loop would hide the failure.
  - Version components are compared as base-10 integers (`10#<n>` in bash arithmetic), so a leading zero is never
    read as octal.
  The step `Compute Docker tags` is renamed `Compute release channels` (`id: channels`) and writes `tags_api`,
  `tags_web`, `npm_tag` and `latest`. The `info` job takes its `npm_tag`, `docker_tags_api`, `docker_tags_web` and a new
  `latest` output from it. `Set release info` stops writing `npm_tag`. The `release` job passes
  `make_latest: ${{ needs.info.outputs.latest }}` to `softprops/action-gh-release`.
- **Deploy scripts are tested with a recording `docker` stub.** A test copies `deployments/example/` into a per-test
  temp dir, puts stub `docker` and `curl` executables first on `PATH`, runs the script with `bash`, and asserts on the
  recorded calls. No real Docker is needed, so the tests run inside the nax sandbox. The harness is a test helper
  created by US-004 (skeleton below).
- **Bash 3.2.** The deploy scripts and the workflow step bodies must run under the `/bin/bash` 3.2 that macOS ships,
  because the tests run them on macOS hosts (koda-wk and the nax runner) as well as on CI's Ubuntu: no `${var,,}`,
  `mapfile`, associative arrays or `|&`, and no `"${arr[@]}"` on a possibly empty array under `set -u` (bash 3.2
  reports it unbound).
- **No early-exit reader on a pipe under `pipefail`.** K7's defect class: `grep -q`, `head` and similar readers that
  exit before EOF make the writer die with SIGPIPE. Feed such readers with a here-string or a file, or read the whole
  stream.
- **Compose project resolution (K3).** Backup and restore of the data volume run inside the Compose project's own `api`
  service: `docker compose -f "$COMPOSE_FILE" run --rm --no-deps --user root --entrypoint sh -v "<host dir>:/backup" api
  -c "<tar command>"`. Compose mounts the project's `koda_data` volume at `/data`, whatever the project name is, so no
  volume name appears in either script. This mirrors `deploy.sh`'s existing `run --rm --no-deps --user root
  --entrypoint chown api` call. The api image is Alpine (busybox `tar`, `find`, `sh`).
- **Backup always dumps (K6).** `backup-db.sh` runs `docker compose -f "$COMPOSE_FILE" up -d --wait postgres` first, then
  dumps. On a first install this initialises the database and writes a near-empty but valid dump, which removes the
  "not running, skip" branch. The dump is complete when its decompressed text contains the line
  `-- PostgreSQL database dump complete` anywhere (pg_dump writes it as the last comment). The script checks the gzip
  and that line, reading the whole decompressed stream (no `grep -q` on a pipe, per the SIGPIPE rule above), and on any failure deletes the partial `koda-db-<ts>.sql.gz`, prints `❌ Postgres dump failed`, and exits 1.
  Postgres is left running afterwards.
- **Rollback order (K4, N1).** Parse arguments, then:
  1. With `--restore-db`: the file must exist and be readable (else `❌ Backup file not found: <path>`, exit 1), and
     `tar -tzf` on the host must list it (else `❌ Backup file is not a valid .tar.gz: <path>`, exit 1).
  2. Pull the target images with `KODA_VERSION=<target>` in the environment (`docker compose -f "$COMPOSE_FILE" pull api
     web`); a failed pull exits 1.
  3. Stop `api` and `web` (unchanged, `|| true`).
  4. With `--restore-db`: restore through the api service, as above, with `KODA_VERSION=<target>` and the archive's
     directory mounted read-only at `/backup`. The command empties `/data` including dot-entries
     (`find /data -mindepth 1 -delete`), then `tar -xzf /backup/<basename> -C /data`.
  5. Update `.env`: replace every existing `KODA_VERSION=` line with `KODA_VERSION=<target>`, append one when absent
     (on a new line even when the file does not end in a newline), or create the file. Copy `.env` to a temp file in
     the same directory with `cp -p` (which keeps its mode), write the new content into that temp file, and `mv` it
     over `.env`; other lines keep their text and order, and a 0600 `.env` stays 0600.
  6. Start `api` and `web` (unchanged).
- **`DATABASE_URL` refusal (K5).** `deploy.sh` reads `.env` (when present) and refuses any active line that assigns
  `DATABASE_URL` (optional leading whitespace, an optional `export ` prefix, `DATABASE_URL`, optional whitespace, `=`,
  with any value, including an empty or quoted one), printing
  `❌ DATABASE_URL is not supported by this example deployment: it always uses the bundled postgres service` and
  exiting 1 before any `docker` call. Commented lines are ignored. A `DATABASE_URL` exported in the operator's shell is
  not refused: Compose never passes it to the API (the `environment:` mapping sets it), and refusing it would break
  deploys from a shell that has a development `DATABASE_URL`.
- **Compose switches (K1).** Both `docker-compose.yml` (root) and `deployments/example/docker-compose.yml` add, under
  `services.api.environment`, `WEBHOOK_SIGNATURE_V1_ENABLED: ${WEBHOOK_SIGNATURE_V1_ENABLED:-true}` and
  `CI_WEBHOOK_REQUIRE_V2: ${CI_WEBHOOK_REQUIRE_V2:-false}`. The defaults are the API's own defaults.
- **Turbo test inputs.** A new `apps/api/turbo.json` (`"extends": ["//"]`) sets `tasks.test.inputs` to
  `$TURBO_DEFAULT$` plus `$TURBO_ROOT$/.github/workflows/**`, `$TURBO_ROOT$/deployments/**`, `$TURBO_ROOT$/scripts/**`,
  `$TURBO_ROOT$/docker-compose.yml` and `$TURBO_ROOT$/openapi-ts.config.ts`. `$TURBO_ROOT$` was checked on turbo 2.11.4:
  a dry run of `@nathapp/koda-api#test` lists `../../.github/workflows/ci.yml` as an input. Only the `test` task is
  overridden; the root `turbo.json` keeps `dependsOn`, `env` and `outputs` through `extends`.

### Test harness skeleton (US-004, novel shape)

No test in the repo runs a shell script against a stub. The helper's shape is fixed here; the stub's internals are the
implementer's.

```ts
// apps/api/test/unit/tooling/helpers/deploy-script-harness.ts
export interface DockerCall {
  argv: string[];          // the arguments after `docker`, one entry per argument
  kodaVersion: string;     // KODA_VERSION in the stub's environment, '' when unset
}
export interface StubBehaviour {
  failOn?: string[];       // the stub exits 1 for a call whose joined argv contains one of these substrings
  pgDump?: string;         // stdout for the call that runs pg_dump (default: a dump ending in the completion line)
  pgDumpExit?: number;     // exit code for that call (default 0)
}
// The stub reads pgDump from a file the harness writes under `dir` (a dump over 1 MiB cannot travel through the
// environment). "A call whose argv contains X" in the ACs means an argv element equal to X, except `pg_dump`, which
// is a substring of the `sh -lc` command element. `failOn` matches the call's argv joined with spaces, after every
// occurrence of `dir` is removed, so a random temp-dir suffix never matches by accident.
export interface ScriptRun {
  status: number;
  output: string;          // stdout and stderr, interleaved
  dockerCalls: DockerCall[];
  dir: string;             // the temp copy of deployments/example, as a real path (macOS /var -> /private/var),
                           // so it equals the SCRIPT_DIR the script resolves for itself
}
// Copies deployments/example into a mkdtemp dir (keeping each script's executable bit: deploy.sh checks
// `-x backup-db.sh`), writes `.env` when envFile is given, puts stub docker + curl first on PATH, and runs
// `/bin/bash <dir>/<script> ...args`. The stub dir also holds a `bash` shim that execs `/bin/bash`, so a script
// that deploy.sh runs through its `#!/usr/bin/env bash` line also runs under bash 3.2. `.env` is written with
// envFileMode (default 0o644) before the script starts. The child's environment is built from PATH (stub dir first) and HOME only,
// plus opts.env: an operator's exported POSTGRES_PASSWORD, KODA_VERSION, DATABASE_URL or COMPOSE_PROJECT_NAME
// never reaches the script. Fixture files a test passes as arguments (an archive, a text file) are created inside
// `dir`, so every path the script resolves with `cd ... && pwd` is a real path. Nothing is removed until
// cleanupDeployScriptRuns() runs in the test's afterEach.
export function runDeployScript(
  script: 'backup-db.sh' | 'rollback.sh' | 'deploy.sh',
  args: string[],
  opts?: { envFile?: string; envFileMode?: number; env?: Record<string, string>; docker?: StubBehaviour },
): ScriptRun;
export function cleanupDeployScriptRuns(): void;
```

### Failure Handling

| Case | Behaviour |
|---|---|
| CI filter: changed-path list larger than a pipe buffer, every path a code path | `code=true` |
| Release: `git ls-remote` fails | the channels step exits non-zero; no tags are computed |
| Release: canary tag | Docker `:canary` only, npm `canary`, `latest=false` |
| Release: older version, not newest of its minor | Docker `:<tag>` only, npm `backport-<version>`, `latest=false` |
| Backup: `up -d --wait postgres` fails | exit non-zero, no dump attempted |
| Backup: pg_dump exits non-zero | `❌ Postgres dump failed`, partial dump deleted, exit 1 |
| Backup: dump lacks the completion line | `❌ Postgres dump failed`, partial dump deleted, exit 1 |
| Backup: data archive `run` fails | exit non-zero |
| Rollback: restore file missing | `❌ Backup file not found: <path>`, exit 1, no `stop` and no `run` call |
| Rollback: restore file not a gzip tar | `❌ Backup file is not a valid .tar.gz: <path>`, exit 1, no `stop` and no `run` call |
| Rollback: target image pull fails | exit 1, no `stop` call |
| Deploy: `.env` assigns `DATABASE_URL` | refusal message, exit 1, no `docker` call |
| Deploy: pre-deploy backup fails | exit non-zero, no migration |

## Out of Scope

- Restoring Postgres from the `koda-db-<ts>.sql.gz` dump inside `rollback.sh`: it stays the documented manual step in `deployments/example/README.md`.
- External Postgres support in the example deployment: the owner ruled bundled Postgres only (2026-11-20).
- The root `docker-compose.yml` `DATABASE_URL`: it is the local build file and keeps the bundled `postgres` URL; only the two signature switches are added to it.
- A `docker compose config` render test: it needs Docker, which the nax sandbox withholds; the Compose change is checked in review.
- Re-pointing Docker `latest`, the `<major>.<minor>` aliases or npm dist-tags already published: no backwards move has happened yet.
- Backup rotation or pruning of `deployments/example/backups/`.
- `apps/api/package.json` `seed:prod` and `apps/api/prisma/seed.ts`: they stay for development and e2e use; only `scripts/seed.sh` is deleted.
- `scripts/smoke-test-cli.sh` and `scripts/bump-version.sh`: unchanged.

## Stories

Eight stories: two workflow stories, one config story, four deploy-script stories, then docs and cleanup. This is one
capability (deployment, CI and release hardening for the example deployment and the two workflows), confirmed with the
owner as spec #1 of the 2026-11-20 review bundle.

**US-001: CI change filter.** Workdir: `apps/api`. No dependencies.
The `changes` job's `filter` step uses a here-string, and `openapi-ts.config.ts`, `deployments/` and the root
`docker-compose.yml` are code paths for PRs and pushes (K7, K19).

**US-002: Release channels.** Workdir: `apps/api`. No dependencies.
`release.yml` moves `latest`, the minor alias, the npm dist-tags and the GitHub latest flag only for the newest stable
version of each channel (K8).

**US-003: Compose switches and test inputs.** Workdir: `.`. No dependencies.
**No-test:** Compose and turbo configuration and one docs line; no test loads these files.
Both Compose files pass the two webhook signature switches (K1), `apps/api/turbo.json` adds the repo-root test inputs,
and `docs/deployment/webhooks.md` says the Compose files pass both switches.

**US-004: Backup always dumps and uses the Compose project.** Workdir: `apps/api`. No dependencies.
`backup-db.sh` starts Postgres, dumps and verifies, and archives the data volume through `compose run ... api` (K3, K6).
Creates the deploy-script test harness.

**US-005: Rollback preflight.** Workdir: `apps/api`. Depends on US-004.
`rollback.sh` validates the restore archive and pulls the target images before it stops any service (K4).

**US-006: Rollback restore and portable `.env` update.** Workdir: `apps/api`. Depends on US-005.
`rollback.sh` restores the data volume through the Compose project and updates `.env` without `sed -i` (K3, N1).

`deploy.sh` refuses a `.env` `DATABASE_URL` assignment (K5) and does not migrate when the pre-deploy backup fails (K6).

**US-008: Operator docs and seed.sh retirement.** Workdir: `.`. Depends on US-004, US-005, US-006, US-007.
**No-test:** documentation and one file deletion.
`deployments/example/README.md` and `docs/deployment/postgresql.md` document bundled Postgres only and the new backup
and rollback behaviour, and `scripts/seed.sh` is deleted (K5, K20).

### Modifies

No existing test breaks: the only test that reads a workflow, `ci-integration-shards.spec.ts`, slices the
`integration-shards` job, which no story changes. The entries below authorise the repo-root files each story changes
outside its `Workdir`.

**US-001**
- `.github/workflows/ci.yml` — the `filter` step's `printf | grep -qE` becomes a here-string; `CODE_PATHS` gains the deployments directory and the escaped openapi-ts config and root Compose file names; `on.push.paths` gains the deployments glob, the root Compose file and the openapi-ts config file; nothing else in the file changes.

**US-002**
- `.github/workflows/release.yml` — step `Compute Docker tags` (`id: docker`) becomes `Compute release channels` (`id: channels`) writing `tags_api`, `tags_web`, `npm_tag` and `latest`; `Set release info` stops writing `npm_tag`; the `info` job outputs read `steps.channels.outputs` and add `latest`; the `release` job passes `make_latest`.

**US-003**
- `docker-compose.yml` — `services.api.environment` gains `WEBHOOK_SIGNATURE_V1_ENABLED: ${WEBHOOK_SIGNATURE_V1_ENABLED:-true}` and `CI_WEBHOOK_REQUIRE_V2: ${CI_WEBHOOK_REQUIRE_V2:-false}`.
- `deployments/example/docker-compose.yml` — `services.api.environment` gains the same two entries with the same defaults.
- `docs/deployment/webhooks.md` — section "Deprecation window" gains one sentence that both Compose files pass the two switches to the API.

**US-004**
- `deployments/example/backup-db.sh` — the running-service check and its skip branch are removed; Postgres is started with `up -d --wait postgres`, dumped and verified; the data volume is archived through `compose run --rm --no-deps --user root --entrypoint sh ... api` instead of `docker run -v koda-local_koda_data`.

**US-005**
- `deployments/example/rollback.sh` — the archive checks and the target-image pull move before `stop api web`; the restore and `.env` update are left to US-006.

**US-006**
- `deployments/example/rollback.sh` — the restore goes through `compose run ... api` instead of `docker run -v koda-local_koda_data`; `sed -i` is replaced by a `cp -p` temp file and `mv`.

**US-007**
- `deployments/example/deploy.sh` — gains the `.env` `DATABASE_URL` refusal after the `POSTGRES_PASSWORD` check; the rest of the script is unchanged.

**US-008**
- `deployments/example/README.md` — the "Notes" bullet that suggests an external `DATABASE_URL` is replaced by a bundled-only statement and the backup and rollback sections describe the new behaviour; leave the documented `.env` lines for `JWT_SECRET`, `JWT_REFRESH_SECRET` and `API_KEY_SECRET` intact, because the API's environment validation spec reads them from this README.
- `docs/deployment/postgresql.md` — the external-Postgres paragraph states that the example deployment scripts support only the bundled `postgres` service.
- `scripts/seed.sh` — deleted.

### Seams

- US-005, US-006 and US-007 consume `runDeployScript` and `cleanupDeployScriptRuns` (US-004). Each story's ACs drive its
  own script through the helper, which proves the helper's contract at every use.
- US-007 AC-9 and AC-10 drive `deploy.sh` (the entry point an operator runs) with the backup's pg_dump failing, which
  proves US-004's verified backup is on the deploy path, not only reachable from `backup-db.sh` directly. They are
  regression guards: `deploy.sh` already runs the backup under `set -e`, so they pass once US-004 lands. The same holds
  for US-007 AC-7 and AC-8, and for US-006's `.env` ACs on Linux, where GNU `sed -i` works; their red step is on macOS.
