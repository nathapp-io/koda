# Koda repository review at `37b396c49`

Reviewed the API, runner, web, CLI, shared packages, build and release configuration, and example deployment on local `main`. This is a risk-based review of the checkout. The earlier [consolidated review](20261120-review-whole-repo-consolidated.md) covers a different commit.

The second pass confirmed two high, eleven medium, and one low finding. It narrowed finding 2 to a stale-lease race and reduced its priority. The evidence table records the checks and controls for each original ID.

## High priority

**1. Turning off notification email disables password recovery.** The reset service passes the account ID to the notification library. Its email preference check returns successfully when the user opted out, and the dispatcher records the message as `SENT`. The user receives no reset link and the delivery record obscures the cause. Send requested recovery mail independently of notification preferences while retaining the account ID on the schedule row. Cover this with a disabled email preference and the real notification service. [Reset send](../apps/api/src/auth/password-reset/password-reset.service.ts#L96) · [Dispatcher](../apps/api/src/email/email-dispatcher.ts#L118) · [Preference update](../apps/api/src/notifications/notification-preferences.service.ts#L102)

**3. The documented PostgreSQL recovery can report success with the wrong data.** The backup is a plain dump without cleanup statements. The guide pipes it into the named application database without requiring an empty target. On an existing installation, tables and keys already exist. Table creation and data loads can fail, newer rows can survive, and default `psql` error handling continues after SQL errors. An operator can bring the app back on a mixture of old and new state. Document restoring into a fresh empty database with writers stopped, error-stop enabled, and verification before switching over. [Restore instructions](../deployments/example/README.md#L97) · [Dump creation](../deployments/example/backup-db.sh#L54)

## Medium priority

**2. Stale-lease cleanup can stall synchronization for every job on a runner.** The API ordinarily prevents concurrent placement of two non-thread jobs for the same repository. The narrower failure occurs when it cancels job A before its assignment acknowledgement arrives, places B, and later fences A’s stale report. If the runner receives B’s assignment before A’s abandon command, B can acquire the repository lock ahead of A’s cleanup. The sync loop then waits for B while B can be waiting for a token delivered by that very loop. Move retirement off the polling path, deduplicate repeated commands, and acknowledge cleanup after it finishes. [Placement guard](../apps/api/src/fleet/jobs/placement-rules.ts#L238) · [Command handler](../apps/runner/src/supervisor/command-handler.ts#L108) · [Lock acquisition](../apps/runner/src/supervisor/job-run.ts#L233)

**4. Backup confidentiality depends on the host's default permissions.** With a typical `022` umask and a traversable deployment directory, the script creates a readable dump, temporarily expands its full SQL to another readable file, and writes the data archive from a root container. Create an owner-only backup directory, enforce private modes for both host and container outputs, and stream the completion check without creating a plaintext copy. [Directory and dump](../deployments/example/backup-db.sh#L36) · [Verification and archive](../deployments/example/backup-db.sh#L62)

**5. Both Compose deployments drop the email configuration.** Rendering the manifests with `SMTP_URL`, `EMAIL_FROM`, and `WEB_PUBLIC_URL` supplied omitted all three from the API service environment. Operators can configure a valid relay in their deployment environment and still leave recovery, invitation, and notification mail unavailable. Forward the three optional settings in both manifests and test the rendered configuration. [Root Compose](../docker-compose.yml#L20) · [Example Compose](../deployments/example/docker-compose.yml#L11) · [API configuration](../apps/api/src/config/email.config.ts#L47)

**6. Temporarily disabling SMTP can permanently fail queued mail.** When SMTP is absent but the public URL remains configured, the dispatcher still claims due rows. Content that passes eligibility reaches a missing SMTP provider, which raises a permanent failure. Restoring SMTP leaves those rows terminal. Gate scheduled claims on email availability and verify that existing pending mail resumes after reconfiguration. [Timer](../apps/api/src/email/email-dispatcher.ts#L50) · [Delivery failure](../apps/api/src/email/smtp-delivery.channel.ts#L36)

**7. Email preparation failures bypass the maximum attempt count.** A repeated database or preference lookup error during content preparation always calls `retryAt`. Only errors inside `sendOne` check `EMAIL_MAX_ATTEMPTS`. Apply the same exhaustion decision to preparation errors and verify the final attempt ends in `FAILED`. [Preparation retry](../apps/api/src/email/email-dispatcher.ts#L99) · [Send retry](../apps/api/src/email/email-dispatcher.ts#L131)

**8. A PR URL on another forge can retire the correct PR's pending rulings.** For a newer RUN under the same configured repository, retirement accepts a reported URL with the same owner, path, and PR number on a different host. The latest-RUN lookup checks the origin, so the two operations disagree about which RUN owns those rulings. Ready-comment selection has the same omission. Share the origin-and-path check across all three paths. [Latest RUN](../apps/api/src/fleet/rulings/prisma-fleet-pr-ruling.repository.ts#L125) · [Retirement](../apps/api/src/fleet/rulings/prisma-fleet-pr-ruling.repository.ts#L166) · [Ready selection](../apps/api/src/fleet/rulings/prisma-fleet-pr-ruling.repository.ts#L195)

**9. An unrelated sync validation error can suppress a valid capability update.** Jobs, events, and capabilities share a request. Any HTTP 400 on that request records its capability hash as rejected. Even after the invalid event is isolated, the daemon suppresses the same hash, leaving the scheduler with stale placement information. Retry capabilities on their own before suppressing them. [Request classification](../apps/runner/src/sync/sync-loop.ts#L193) · [Hash suppression](../apps/runner/src/sync/sync-loop.ts#L124)

**10. Cancelling a thread as its stream opens can restart its heartbeat after completion.** Startup publishes `RUNNING`, awaits stream creation, and then starts a timer. Cancellation can finish and stop the heartbeat during that await. Startup subsequently installs a fresh heartbeat whose loop checks only `halted`, so it can keep writing snapshots for a terminal job. Coordinate stream startup with close and check the terminal state before scheduling the timer on both thread paths. [Repository thread](../apps/runner/src/thread/thread-job-run.ts#L385) · [Workspace thread](../apps/runner/src/thread/thread-job-run.ts#L455) · [Heartbeat loop](../apps/runner/src/thread/thread-job-run.ts#L837)

**11. A short access-token lifetime or long refresh-token lifetime can interrupt a valid web session.** With a five-minute access token, a protected page opened after six minutes still carries the 15-minute access cookie. Its presence suppresses server-side refresh and the expired token makes the user anonymous despite a valid refresh token. A refresh lifetime longer than seven days is also cut short by its cookie. Align cookie expiry with token expiry and test a protected page after the access token expires. [Cookie lifetime](../apps/web/server/utils/api.ts#L49) · [Refresh decision](../apps/web/server/utils/session-refresh.ts#L39) · [Identity response](../apps/web/server/api/auth/me.get.ts#L22)

**12. CLI logout can delete a credential for another deployment.** Authentication can resolve from an environment variable or a project-selected profile. After logout succeeds, the CLI always deletes the global key. Using deployment B's temporary user token can therefore remove deployment A's saved credential. Carry the credential source through logout and clear only the matching stored credential. [Logout](../apps/cli/src/commands/auth.ts#L86) · [Resolution](../apps/cli/src/config.ts#L165) · [Deletion](../apps/cli/src/config.ts#L196)

**13. Ticket creation ignores both defaults saved by `koda init`.** Initializing a project with a default ticket type and priority writes both values. Creation still rejects a missing type, and passing a type explicitly still omits the configured priority. Resolve flag values first and then project defaults before validating the request. [Initialization](../apps/cli/src/commands/init.ts#L71) · [Creation](../apps/cli/src/commands/ticket.ts#L116)

## Low priority

**14. CLI login reports an invalid credential as a network outage.** The generated client throws the API's response body. The login handler checks HTTP-status properties that the standard error envelope lacks and prints `Could not reach API: [object Object]`. Use the existing envelope-aware error mapping and distinguish an HTTP rejection from a transport failure. [Login handler](../apps/cli/src/commands/login.ts#L52) · [Shared mapping](../apps/cli/src/utils/error.ts#L44)
