PAY-142 · opened Oct 3 by Omar Haddad

Refund webhook retries forever when the provider returns 429

In progress Critical Bug payments-core

Description

When the refund provider responds 429, our webhook handler re-queues the event without a backoff, so one bad refund can retry forever and flood the provider.

Repro: issue a refund for a declined charge and watch refund-webhook logs.

retryRefund(event)   // no backoff, no max attempts
  → POST /refunds/:id/retry

Activity

OH
Omar HaddadOct 3, 14:02

Provider docs say 429 means "slow down", not "failed". We should back off and cap retries instead of looping.

Reproduced on main. Root cause: the retry queue uses a fixed 1s delay and never increments an attempt counter. Fix incoming with exponential backoff (max 5 attempts) + dead-letter after that.
